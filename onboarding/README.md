# Onboarding package

`@apparent/onboarding` is a TypeScript setup and practice owner. It exports a pure controller and React contribution factory. It owns versioned progress, resume/defer/completion, coaching stages, practice association, and manual paste confirmation. It consumes the exact packed public `@apparent/record/capabilities` contract; it imports no Record implementation, EngineClient, Electron API, or Rust.

## Build and tests

Run `npm ci`, `npm run typecheck`, `npm test`, `npm run build`, and `npm pack --dry-run` in this directory. Development dependencies are the committed public Record tarball `vendor/record-0.1.0-afd73fb.tgz`, packed from candidate PR #674 head `afd73fbdca110ee866d32b062219cab762f20f17`, SHA-256 `61bddb5d86bf71cb9566c0071f2e22e2e226553291d1bd5c90eaa45237853ab3`, and host contract tarball `vendor/apparent-app-contracts-0.1.0.tgz` (SHA-256 `f201df63ecb50abe7cf74c1f54469360e37ad22d6d5c6850edfc84024c7d8e14`). The lockfile pins their packed declarations/runtime; Onboarding install does not build either source tree. Refresh these pins only when the corresponding public artifact changes. Tests use `createRecordFixture` from the Record package and compile the factory against the exact host API artifact. This proves fixture behavior, not installed behavior. No Cargo/rustc is required.

The shell injects the canonical `Button` from `@apparent/ui/button`, supplies its canonical appearance tokens, and loads `@apparent/onboarding/styles.css`. The build bundles the public Record artifact-open helper from the pinned package; runtime code does not need a sibling checkout or Record package installation. Public declaration consumers supply compatible Record types. React remains host-provided.

## Standalone permission repair slice

`PermissionRepairController.activate(requestedIds)` and `createPermissionRepairContribution` are an owner-specific activation seam for the standalone **Access** screen. A composition host supplies a long-lived public `RecordClient`, canonical `Button`, exact permission requirement IDs and its existing close callback. The screen may be opened after the tour was completed or deferred; it preserves tour milestones and status, and closing with **Later** does not defer or complete the tour. Repeated activation for the same open request reuses the current view. Host composition must retain one setup surface and keep any active tour suspended until repair closes; this package does not register a second stream route or window.

The consumer accepts only `screen-capture`/`screen-recording`, `microphone`, `accessibility`, `camera`, and `speech-recognition`, then requires every explicitly requested row to be present, connected, granted and usable. `required: false` does not weaken an explicit repair request. Empty requests, unknown IDs and `input-monitoring` are rejected. The row action comes only from that row's `allowedRepairActions`: first `not-determined` uses an allowed system request, a repeated accepted request or denied state opens allowed System Settings, and granted-but-unusable relaunch state remains blocked unless Record allows its safe-relaunch command. Status/readiness and relaunch remain OS/provider facts; acceptance means dispatch only. Ready closes after 800 ms of continuous usable facts within the same provider epoch; polling does not restart the deadline. Unmount, close, retargeting and disposal cancel owned timers and invalidate unfinished UI requests without stopping capture.

Safe relaunch requires the same injected owner `ProgressStore`. Before dispatch it CAS-publishes only the legacy `relaunchedAt`/`reopenFix` metadata, preserving tour state. Conflicts and unknown publication prevent dispatch. For granted screen access requiring relaunch, a one-second timer attempts one automatic reopen per activation; the persisted two-minute cooldown also survives a new controller/process. An explicit **Reopen Apparent** action may override that automatic cooldown. Missing storage prevents relaunch, and Record still enforces busy/finalizer safety. This is consumer policy against fixtures, not a tested native restart or config provider.

Record does not yet expose a blocked-intent event and this checkout has no production host activation wrapper that calls the repair seam. Platform composition must route its existing permission-blocked outcome to one `PermissionRepairController.activate(requestedIds)` handle while preserving the existing setup owner/window. Repair host wiring and native permission production are pending. Tests use the packed public Record fixture, injected CAS storage and mounted React controls; they prove consumer behavior only, not operating-system effects, installed routing, focus, or capture exclusion. The legacy native fix screen remains the fallback until host adoption and its affected platform permission/focus/capture-exclusion checks are accepted.

## Record contract mapping and adoption limits

Onboarding imports the public capabilities from the packed Record package. Commands use a unique request ID and the observed provider epoch/revision. `accepted` means dispatch only; only provider facts or `applied` plus readback can advance a milestone. Disposal detaches lesson observation; bounded reservation cleanup waits for any late arm and cancels only that admission. It releases observation on consumption/cancellation/expiry, provider replacement or a five-minute deadline; it never stops a capture.

Practice reserves the next shortcut as local-only before prompting the user, persists its identity, and accepts only the newly consumed matching capture with local-only readback and shortcut evidence. Deferral/disposal cancels an unconsumed reservation; consumed capture is never stopped. The fixture proves the policy consumer, not a production adapter: no native shortcut reservation producer or delivery enforcement/readback adapter exists yet. Permission continuation requires all required requirements usable now with no relaunch pending. Shortcut continuation requires a nonempty effective binding, no draft, and confirmed registration; an externally-managed boolean alone is not proof. Pen selection advances only after authoritative readback of the explicitly selected effective value, including readback delivered after command acceptance and the animation completes (or reduced motion is enabled).

Record #674, merged as `9efc9acf1e49de58e8099d4d04857271d35e3194`, names the donor's coral, purple, blue, and green palette as `PenColor`, separates it from drawing tool modes, and supplies typed picker and accepted-stroke outcomes. Onboarding uses that exact type and fixture readback. The fixture proves consumer behavior only; the production pen writer, native picker/stroke mapping, shortcut reservation and enforced local-only delivery producers remain unavailable.

Processing, save and copy are separate outcomes on the associated capture. Paste confirmation is a manual user action; no private composer is observed. Locate calls `hasConfirmedArtifactOpen(snapshot, captureId)`, which requires the saved exact capture and current artifact identity with `viewer-ack` or `os-observation`. A matching proof completes automatically after the user confirms paste. Dispatch alone never completes the lesson. #665 added the typed fact/helper and fixture coverage; no production provider emits the confirmation yet. Installed setup remains pending at Locate until Record maps trusted viewer acknowledgement or supported OS observation to the saved artifact identity. Never infer opened/watched from focus, process, path, or dispatch success.

Practice uses the public request-scoped arm/cancel facts and checks the consumed admission ID against the exact capture, shortcut fact, and enforced `delivery: "local-only"` readback. It does not issue a second menu start. This fixture covers consumer policy only; the installed adapter must enforce these facts or refuse adoption.

## Persistence, host adoption and rollback

`ProgressStore` requires read and compare-and-swap `(revision,value)`, distinguishing saved, conflict/current snapshot, and unknown publication. Unknown is not success. The only store in tests is in-memory. Installed progress must use the sole transactional writer after verified cutover; no filesystem read/modify/write or competing writer is supplied. The shell provides activation reasons (`firstLaunch`, `settings`, `resume`) and declarative coach placement, then renders `createOnboardingContribution({controller, Button, close, onManualPasteInstructions})`. No arbitrary IPC/window/URL/filesystem effect is exposed. There is no production host/preload adapter or second installed surface.

Privileged bootstrap may call `adoptOnboardingProgress(backend)` using the public `LegacyAdoptionBackend` from #720. The host must first quiesce the legacy journey writer. The helper reads the atomic owner/legacy snapshot, prefers an existing owner entry (including stored null), decodes legacy progress with this owner’s codec only when the owner is absent, and submits the exact legacy presence/value as the adoption compare condition. It returns `ready`, `conflict` with the fresh snapshot, or `unknown`; it never retries a write or treats transport ambiguity as success. Unsupported progress rejects without a write. After a confirmed result the host can bind its existing owner progress store and activate the factory. This helper does not open config, construct a backend, or switch installed routing. The refreshed packed host contract is built from committed main containing #720; its SHA above pins the added adoption types. Native lock/CAS evidence remains owned by Platform, and its #723 fixed helper still requires production artifact admission.

The shipped Preview 0.12.2 journey in the read-only release-baseline checkout is the design donor for frog/puddle artwork, approved copy, and pen-hop motion. Only the frog asset is copied here. Host routing remains unchanged until this contribution and its adapters are accepted. The adoption helper preserves legacy keys and never dual-writes them. Installed cutover and rollback must explicitly choose the active route and progress authority; no installed adoption or routing change is performed here.

Remove the donor only after typed Record capabilities, truthful local-only admission, production artifact-open evidence, transactional progress writer, host contribution/preload, shared UI checks and affected native seams are verified; existing resume/defer/completion state is preserved; and every source/build/package consumer has moved. A passing fixture package is not installed adoption or native proof.
