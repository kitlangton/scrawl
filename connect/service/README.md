# Apparent Connect API Worker

Private Cloudflare Worker, D1 metadata and R2 bundle bytes. Public UI is owned by the site. See [`../../connect/docs/hosted-api.md`](../../connect/docs/hosted-api.md) for the shared browser/native contract.

## Local proof (no Cloudflare account or credentials)

```sh
cd connect/service
npm ci
npm test
```

Tests bundle the actual Worker and run it in Miniflare/workerd with real local D1 and R2 bindings. OAuth tests use a controlled HTTP provider with RSA-signed ID tokens, including invalid signatures and claims. This is **not live Google verification**. Other API security tests seed synthetic accounts/tokens directly to isolate authorization behavior. The suite includes a streamed 90,000,000-byte upload and deletion while a real upload is in flight.

Production code counts streamed chunks through `FixedLengthStream` and asks R2 to verify SHA256 natively using `R2PutOptions.sha256`, not JavaScript per-byte hashing or whole-movie `arrayBuffer()`. Completion checks R2's stored checksum, not custom metadata. Retries validate the supplied bytes in a separately registered temporary object and delete it without replacing the original. D1 batches and conditional updates preserve atomic manifests, admission, token approval, publication and tombstones. Failed/stale upload keys are registered before writing; cleanup revisits tombstones to remove late uploads. Cleanup rotates through at most 1,000 attempt keys per run, rather than starving later pages. Tombstone/attempt metadata is deliberately retained; monitor D1 growth before broadening this limited beta.

Runtime modules in `src/*.ts` use strict TypeScript and official Workers binding types; `src/types.ts` contains only binding/domain declarations. `npm run typecheck` checks without emitting files. `npm run build` runs that check before bundling `src/worker.ts` to `dist/worker.js`. Tests, dev and deploy all run this checked build first. JavaScript tests remain in `test/*/*.test.mjs`. `skipLibCheck` skips dependency declarations that also reference unsupported Bun/Node database adapters, not application checks. Builds must retain `--conditions=workerd --external:node:*` and Wrangler's `nodejs_compat`: selecting Better Auth's browser async-context fallback breaks independent concurrent requests. Local browser OAuth needs secure cookie-compatible routing and a controlled provider or authorized Google test client. `wrangler.toml` contains intentionally unusable resource/origin placeholders. No test provisions remote resources.

## Better Auth ownership and failure boundaries

Exact dependencies `better-auth@1.7.15` and `@better-auth/oauth-provider@1.7.15` own Google OIDC verification/state/PKCE, signed browser sessions, device issuance/consent, opaque access credentials and refresh rotation/replay. The Worker exposes only the existing named compatibility routes, not the raw Better Auth handler, alternate signup/login, dynamic registration, management or token endpoints. Per-device OAuth clients are registered server-side. Account linking is disabled; provider access/refresh credentials use Better Auth's supported at-rest encryption. Its 1.7.15 option leaves provider ID tokens plaintext despite the declaration comment, so supported account hooks discard those after verification; this app does not need federated end-session tokens. Existing capture account IDs remain SHA-256 of `https://accounts.google.com/<subject>`; email is not identity. Admission hooks preserve the 20-slot gate and existing account preferences/captures. Login/refresh never enroll decryption keys or create share capabilities.

`auth_grants` is an application authorization allowlist, not a second token generator or rotation protocol. One library client per device grant isolates the library's client/user family invalidation from sibling devices. Every bearer lookup checks the library token's hash/expiry/revocation and the durable grant tombstone. Refresh checks that same immutable grant; revocation writes the tombstone **before** fallible provider cleanup. D1 triggers also atomically tombstone the grant when the library deletes an unexpired access row or any refresh row. This covers partial family invalidation reached after a stale preflight read; deleting an ordinarily expired access row does not revoke a healthy refresh grant. A simultaneous mint or surviving orphan row cannot regain authorization. Browser logout deletes only the browser session; provider token foreign keys use `ON DELETE SET NULL` for that session.

D1 has no interactive transaction. The pinned library consumes a predecessor with CAS, then writes its successor/access/replay separately. Its supported replay interval is 30 seconds. A stored replay returns the same pair across Worker restart; concurrent losers without a stored response receive transient 503 during that interval. After the interval, reuse or an incomplete rotation tombstones that device and returns 401 `reauthorization_required` **before** fallible family cleanup. An interrupted successor/replay write is fail-closed, not guaranteed seamless recovery: a device may need explicit reapproval. Initial approval/token issuance interrupted before application binding or response persistence can likewise require a new device flow. No custom recovery mint or vendored auth fork hides those limits.

Lifecycle tests use real library SQL with deterministic fault/barrier wrappers, shared D1 across two workerd isolates, response loss and isolate reload. They are local persistence/race evidence, not a physical D1 outage or live Google test. Scheduled cleanup clears expired device/replay envelopes and terminal per-grant client credentials, preserving live devices, grant tombstones and spent budgets. Retained identity/grant metadata still needs growth monitoring.

## Deployment checklist (parent authorization required)

The gated main-branch delivery workflow and its separate activation prerequisites
are documented in [`../../enablement/docs/continuous-delivery.md`](../../enablement/docs/continuous-delivery.md).
It never applies migrations or initializes the budget ledger.

- Discover the actual Cloudflare account/routes and existing resources first; do not deploy this template blindly.
- **Local SQL budgets pass; remote Free verification is still blocked.** See the measured operation counts below. The template omits the Paid-only `limits.cpu_ms` override. Local native-checksum tests and statement counts do not prove Free's 10ms CPU limit. Do not activate Paid or deploy without the parent's separate decision.
- Configure an authorized D1 database and private **Standard** R2 bucket. Disable public `r2.dev`/custom-domain access and direct client credentials. No Infrequent Access transitions or metered integrations. Keep bucket lifecycle deletion rules off unless they preserve the service's live seven-day retention contract. Verify Workers/D1 Free and a fail-closed API route separately; no Paid upgrade is authorized here.
- Configure `SITE_ORIGIN=https://app.tryapparent.com` and keep `API_ORIGIN=https://hosted.tryapparent.com` (including the existing Google callback). Set optional `LEGACY_SITE_ORIGIN=https://hosted.tryapparent.com` during transition so old browser pages retain exact credentialed CORS/CSRF access. Cross-site cookies are not supported. Static `/connect` and `/connect/device` plus legacy `/hosted` aliases stay with the site. This rename needs no database migration or credential rotation.
- Fresh databases apply `0001.sql`, `0002.sql`, `0003.sql`, then `0004.sql` with reviewed D1 migration tooling. **Before `0002`'s zero seed, stop writes and verify the exact bound R2 bucket is fresh and empty.** SQL cannot establish bucket emptiness. The seed is withheld if D1 already has captures/attempts; an existing bucket/database requires stopped-writes inventory and reviewed conservative reconciliation. Never recreate/reseed the ledger. Reapplying migrations errors rather than resetting counters.
- Existing databases already through `0003` apply **only `0004`**, after backup/review and while old writers are stopped. It adds Better Auth/provider tables and `auth_grants`, then retires `sessions`, `oauth_states`, `devices` and `tokens`. This deliberately invalidates old credentials/in-flight authorizations, **not** accounts, captures, shares, quota reservations or spent budgets. Coordinate the matching Worker/client cutover; rollback needs the reviewed backup rather than launching old code against the new schema. Legacy bearers/renewal credentials return 401 `reauthorization_required`; old browser cookies are anonymous and need one-time login. The same Google subject retains its account and captures after login.
- Configure `GOOGLE_CLIENT_ID`, secret `GOOGLE_CLIENT_SECRET`, secret `TOKEN_ENCRYPTION_KEY` (32 random bytes base64), and a separate high-entropy secret `BETTER_AUTH_SECRET` (at least 32 characters; missing/short values fail closed). Never put real secrets in TOML or source. Better Auth uses its secret for signed cookies, encrypted provider credentials and library replay material. Do not rotate either encryption secret without a reviewed credential/flow invalidation or compatible key-transition plan. The existing capture/share encryption implementation is unchanged.
- Register exact `API_ORIGIN/auth/google/callback` in the approved Google OAuth client. Discovery defaults to Google's fixed HTTPS URL. `OAUTH_DISCOVERY_URL` is only for controlled signed-provider tests; do not override it for production Google sign-in. Old individual `OAUTH_*` endpoint overrides are retired.
- Confirm Google consent-screen beta/test-user rules with the owning account. No production sign-in has been run here.
- Enable the 15-minute cleanup cron. Quota and authorization expire immediately even when cron fails. Monitor cleanup failures/backlog and D1 metadata growth. A staging object can outlive its quota reservation briefly, but can never be downloaded through the API after tombstone/expiry.
- Keep request/event logs disabled or explicitly redact URLs, Authorization, Cookie, OAuth query codes/state and response tokens in any upstream logging system. The Worker never logs requests, exceptions or provider bodies. Wrangler observability is off in this template.
- Smoke-test actual CORS/cookie routing, live Google claims, 90MB request handling and cron in an authorized staging environment before production. Local workerd proof does not establish remote account configuration.

## Deliberate v1 limits

500,000,000 bytes per account, at most 20 beta accounts, seven days from reservation, 24-hour pending-upload timeout, 512 files per capture, 90,000,000 bytes per file, 128KiB JSON, 128-character exact allowlisted paths. No billing, public object URLs, multipart protocol, account deletion UI or admin promotion route is implemented here. Separate read/upload authorizations have immutable scope/grant ID, one-hour access credentials and rotating 30-day refresh credentials; reported lifetimes are remaining seconds. Revocation denies the entire device grant, including outstanding access and renewal. Browser sessions last seven days; logout revokes only its own session.

## Fail-closed initial beta spending guard

`r2_budget` is one global D1 row, shared by accounts/tokens/Worker instances. Initial **lifetime** caps are **500,000 Class A**, **5,000,000 Class B**, and **9,500,000,000 physical-attempt bytes**. There is no calendar reset, caller-selected period, redeploy initializer or reset API. The source validates integer/nonnegative ledger values and caps no greater than those ceilings. Missing tables/row, invalid state or reservation database failure return JSON `budget_unavailable` (503); exhausted valid capacity returns `budget_exhausted` (503). Clients must retain the complete durable upload job for retry/operator resolution, not erase the capture, shrink the manifest or silently omit files.

Before every controlled R2 PUT/GET/HEAD, D1 atomically reserves its operation allowance. Completion reserves the whole file count once before its HEAD loop, including unused grants after an early missing object. Ready completion and metadata reads need no R2 allowance. Failed/canceled/checksum-invalid provider attempts and duplicate retries consume operations permanently. Authentication, owner/scope, manifest/path and ordinary expiry denials precede the gate. All runtime R2 access is confined to `src/storage.ts`, with a nonempty TypeScript source-inventory test; there is no LIST bypass. Free DeleteObject remains allowed at every cap.

Each PUT atomically grants one A operation, its exact manifest size and a new unique attempt/key before opening R2. Stream size/checksum enforcement is unchanged. Physical charges include published, in-flight, duplicate, orphan and tombstoned objects, not just live logical quota. Eviction/expiry does not release physical capacity. A durable `terminal` marker is written only after the unique provider PUT and body stream both settle. Successful deletion can release its bytes once in a conditional two-statement transaction with the cleanup stamp. Cleanup snapshots terminal eligibility **before deletion**, so a PUT settling after that deletion cannot be released by that sweep. Failed deletion/stamping stays retryable. An uncertain/crashed grant without a terminal marker stays charged even after repeated absent-key deletions; reconciliation needs a separate quiescent operator review. Keys/permits are never reused.

The 500MB account quota remains a maximum, **not a guarantee that all 20 accounts can be physically full together**. The 9.5GB ceiling can reject an upload with logical quota remaining. These guards bound this Worker's controlled R2 work; they are **not an accountwide dollar cap**. Other credentials/resources, provider billing semantics, stored bytes during outages, D1 rows/storage and Free CPU still require operational verification. Billing alerts notify; they do not stop spending.

## Bounded Free audit (not deployment approval)

Official limits: [Workers](https://developers.cloudflare.com/workers/platform/limits/), [D1](https://developers.cloudflare.com/d1/platform/limits/), [R2 checksums](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/). Workers Free permits 10ms CPU per HTTP request and cron invocation. Its 50 external subrequests are distinct from 1,000 internal-service subrequests. D1 separately documents **50 SQL queries per Free invocation**, 1,000 on Paid, and 100 bound parameters per query. A batch does not make its individual SQL statements disappear.

`test/budgets.test.mjs` wraps real local D1/R2 bindings to count submitted statements and operations. It verifies the unchanged full 512-file contract, without claiming Miniflare enforces remote account limits:

- Admission: **5 SQL statements**, down from 516 (one bearer lookup, one existing-ID lookup, a two-statement transaction, one live-capture lookup). The transaction inserts the reservation and all 512 files using `json_each(?)`, preserving the eviction trigger and atomic rollback. It binds six parameters for the reservation and two for the files, not a giant parameter list. Existing-ID retries use three statements; a failed insert can add one recovery lookup.
- Completion: **512 R2 heads + 6 SQL statements**, including one bulk B reservation (518 combined internal operations). Insufficient budget: **5 SQL, zero HEAD**, pending unchanged. Ready retries use two SQL and zero R2. CPU remains unverified remotely.
- A full 1,000-attempt cleanup: **30 SQL statements + 10 R2 deletes** (40 combined). Expiration and selection use two statements; each 100-key page uses one delete and two set statements for conditional physical release/stamping, followed by eight auth/rate cleanup statements. No per-object SQL. Injected first-page delete/stamp failures submit **2/4 SQL + 1 delete**; tenth-page failures **20/22 SQL + 10 deletes**, followed by a successful 30/10 retry. Failed deletes never advance the stamp; stamp failure rolls back release. Tombstones remain for late PUTs. Statements inside batches count individually.
- PUT: **7 SQL + 1 PUT** for first publication; **9 SQL + 1 PUT + 1 delete** for a correct duplicate; **8 SQL + 1 PUT + 1 delete** for a checksum failure; **6 SQL, zero R2** for budget denial. A tombstone after PUT, losing publication, deletion and subsequent 404/catch cleanup uses **12 SQL + 1 PUT + 2 deletes** (15 combined). The audit exercises these failure branches without weakening checksum/ownership rules.

Budget tests first failed against the prior implementation at 516 admission statements and 1,007 cleanup statements. They now enforce at most 50 SQL statements and 1,000 combined SQL/R2 operations, including scheduled outcomes (Miniflare returns `outcome: exception` rather than rejecting the scheduler call). Tests also cover 20 accounts with 60 captures each, 512 files on each of the first account's existing captures, eviction isolation, full-manifest retries, rollback after an injected file-insert failure, 2,001 attempts across accounts, repeated rotation, late arrivals and injected delete/stamp failures. Existing concurrency, ready-state and streaming tests remain in the full suite.

Only manifest insertion and cleanup stamping had per-row SQL loops. Account usage, slot admission, quota eviction, capture expiration and auth cleanup remain set queries; file transfer and device routes use a fixed number of statements. Completion still performs one R2 head per file (at most 512), not SQL per file. The byte quota does **not** bound capture/file/attempt counts: zero-byte files and repeated uploads are legal, and tombstone metadata is retained. Statement counts are bounded independently of those cardinalities, but SQL scan time, daily D1 rows read/written, database growth and remote CPU remain unproven. No claim of a finite worst-case data volume or remote Free viability follows from this local audit.

No contract limits were reduced and no multipart/queue protocol was added. Spending tests use real local D1/R2, small caps written to test D1 rows, two Worker instances sharing bindings, held-provider/stream barriers and real transaction faults. They cover cap races, retry accounting, missing/invalid state, crashes before PUT/terminal marker, late PUT after delete, terminal snapshot races, one-time release, eviction overlap and restart/migration rerun. These are local proofs, not live billing or Free CPU proof. Parent owns separate security review, exact changed-backend native integration, account configuration and any staging authorization. No provisioning, plan change or remote CPU measurement was performed here.
