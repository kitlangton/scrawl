# Connect product analytics

The collector is separate from account admission, storage/spending ledgers and public recording sharing. Collection capability is enabled by default, not an off-by-default experiment or a request for another activation approval. Publishing code does not silently enroll accounts: reviewed disclosure and affirmative account/browser consent still govern sends. Correct deployment bindings, ordered migrations and independent production acceptance remain required. Issue175 remains open for the requested metrics; dashboard installation alone is not acceptance.

## Event and privacy contract

The EU project uses secret `POSTHOG_PROJECT_TOKEN`. Runtime defaults are `POSTHOG_ENABLED=true`, `POSTHOG_HOST=https://eu.i.posthog.com` and `POSTHOG_ENVIRONMENT=production`; the deployment renderer and template make those defaults explicit. A missing token or invalid configuration fails closed. Explicit `POSTHOG_ENABLED=false` remains a kill switch, not the shipped default. A separate `analytics_control.enabled` database switch also gates collection. Additive migration `0007.sql` enables that control once; it is never reset at startup or on every deploy, so a subsequent operator stop persists. Existing accounts start with no consent. `POSTHOG_EXCLUDED_ACCOUNT_IDS` is an optional exact-ID exclusion, never a substitute for consent.

Stable provider identity is `account:<opaque64hex>`, not an email. Qualifying events are `connect_account_created` (only explicit pre-enrollment before creation), `connect_device_connected` (first authoritative post-approval grant binding) and `connect_upload_completed` (pending→ready after complete object verification). Login alone is not an active-user event. `connect_storage_snapshot` is a daily system gauge, not user activity. No historical signup or activity is backfilled after consent. Coverage starts with consent and activation; opt-out and missing history remain visible reporting limitations.

Only allowlisted actor/environment/outcome, opaque identity, occurrence time, UUID, manifest-byte and storage/reservation quantities are exported. No email, recording ID, path, content, transcript, encryption public/private key, session/CSRF/device credential or capability URL is an analytics property. Public recording-link recipients are not instrumented. Browser visits are a separate consented stream and must not be combined with account activity as one DAU count.

Upload statistics deduplicate UUIDs before sum/mean/median, not byte values: two distinct same-size recordings are two uploads. Storage reports select the latest gauge per account before aggregating, including zero-storage accounts. Logical retained size and unreleased reservations are not measured R2 object size or exact cleanup backlog.

## Account-owned consent

`GET /v1/analytics/consent` requires a verified browser session. It returns `{available,consented,revision,noticeVersion}` without enrolling the account or creating a preference. `available` requires valid deployment configuration and global control; a disabled deployment does not forget an existing explicit choice. Notice version is `product-analytics-v1`.

`POST /v1/analytics/consent` requires the same cookie, exact trusted Origin and session CSRF token. The body is `{consented:boolean,revision:string|null,noticeVersion}`. New opt-in requires the current notice version and the exact server revision the browser read; unknown fields and another account ID are rejected. Devices/bearers cannot manage human consent. Withdrawal is available while delivery is disabled and never requires accepting a newer notice.

Choices are transactional in D1. Opt-in records its notice version and server timestamp; an identical positive choice retains the consent generation and pending events. Withdrawal deletes positive consent and pending outbox rows, while retaining a server-owned choice revision. This tombstone prevents an older in-flight opt-in from restoring a deleted row. An explicit operator deletion also rotates the revision. Re-enrollment after a fresh choice gets a new consent identity; stale retries and old batch acknowledgements cannot inherit that later permission. Account deletion removes its positive consent, outbox and choice metadata.

The final database authorization is the export cutoff: withdrawal blocks later authorizations, not a batch already authorized beforehand. Already-admitted sends may finish. Browser preference is independent; withdrawing account analytics does not silently modify an anonymous browser choice, and neither choice is completed provider erasure.

## Browser controls and disclosure

Public and Connect share the small SDK-free `shared/analytics/browser.ts` mechanism. With a valid public ingestion key, capability defaults on: `PUBLIC_POSTHOG_TOKEN`, optional `PUBLIC_POSTHOG_ENABLED` (default `true`), fixed EU `PUBLIC_POSTHOG_HOST` and `PUBLIC_POSTHOG_ENVIRONMENT` (default `production`). An explicit false, invalid configuration or missing key suppresses it; a personal/API-management key is never embedded. Website CD supplies these build inputs to both packages. An unset project key is a configuration failure, not an off-by-default experiment.

On `/`, `/connect` and legacy `/hosted`, the visitor gets equally available Allow/No thanks choices and disclosure identifying **Simon van Laak / simon@tryapparent.com**. First-party storage holds only the notice-versioned choice, its timestamp and permitted opaque analytics identities; it expires after 180 days. GPC/DNT, blocked storage, expiry and cross-tab withdrawal suppress browser sends. If storage is unavailable, disclosure and No thanks remain available for this visit, Allow is disabled, and neither a choice nor telemetry is persisted/sent. A corrupt preference is ignored, not treated as permission. No autocapture, session replay, page title, query, fragment, raw referrer or campaign string is sent. Acquisition/platform labels are allowlisted. Provider requests omit cookies and referrers; PostHog still receives normal network metadata such as an IP address and browser headers.

Browser pageviews and explicit download clicks remain separate from authenticated activity. Linking requires both browser consent and a server-issued consented account analytics identity. Each account-linked browser send rechecks that identity through the session API before transport; failure drops the send, and an observed mismatch clears the old link. The successful server identity read is that browser send’s authorization cutoff; already-authorized sends may finish. Account changes, withdrawal, logout and stale asynchronous responses cannot carry a previous link forward. Public recording recipients, device-approval routes, shared-link management and unknown/private paths are not instrumented. Sign-in, upload/read approval and account-consent reads never create analytics permission.

The signed-in account page has an independent **Optional account analytics** control. Writes use the authenticated CSRF API and read back the exact revision before confirming. Withdrawal stays available when delivery is disabled or an opt-in is pending; an unconfirmed/malformed reply is not shown as a saved choice. Disclosure states provider-default retention, the admitted-send cutoff and that withdrawal is not completed erasure; access/correction/erasure/restriction/portability and complaint routes are stated without promising a physical-deletion deadline.

`connect/web`'s normal tests include the packaged account-control scenarios. Cross-owner enabled-client proof is `npm run test:analytics` there, after both packages' locked dependencies are installed; it builds only separate `dist-analytics-test` outputs, uses synthetic identities and intercepts all provider transport. It never replaces production `dist` or proves actual deployed ingestion. Website delivery runs it before publishing the composed artifact.

## Delivery and operations

The bounded outbox has a 10,000-row limit, a 24-hour queue lifetime and bounded batches. Overflow/expiry is disclosed through the aggregate drop counter, not invented complete coverage. Requests require a successful HTTP result plus exact provider acknowledgment `status: "Ok"` or legacy numeric `1`. Ambiguous acknowledgments retain stable UUIDs for retry. Provider retries may duplicate raw rows; reporting must deduplicate explicitly.

PostHog's existing-plan retention defaults apply. The free query window is not a physical-deletion promise. Local queue expiry is separate. Exact-target provider deletion is asynchronous; accepted deletion or absent person records do not prove event erasure. Keep the earlier synthetic-erasure follow-up owned without re-submitting it or making provider latency an unrelated deployment blocker. Do not infer deletion-write authority from read-only plus Dashboard/Insight write scopes.
