# Apparent: Agent Instructions

Apparent records screen, voice, cursor, clicks and ink so a human can point, talk and draw while an agent builds. It produces `.apparent` bundles for inspection and handoff. Supported platforms are **macOS and Linux**; do not add Windows support, tests, release assets or new docs. Existing Windows code is not a support promise; retire it only in a separately scoped, verified change.

## Product invariants

- Avoid implicit state machines: name workflow states and allowed transitions explicitly; prevent invalid combinations of flags.
- Minimize human effort: capture, marking and handoff should be quick. Record known window, element, URL and session context instead of making agents infer it from pixels or vague references.
- Keep images visual and text semantic. Preserve time-aligned transcript, interactions and absolute paths in bundle text; avoid rasterized captions/card chrome. Cut keyframes on meaningful action or visual change, not speech pauses; retain full frames when cropping. See `capture/engine/docs/keyframes-and-text.md`.
- Persist user-controlled settings and feature flags in documented, inspectable config (currently `~/.config/apparent/config.json`). Settings writes update it; file edits apply at a documented time. Preserve unrelated keys and secrets. Reconcile OS-owned effects such as permissions and login registration; config values alone do not prove application. Active capture state is runtime state, but must be discoverable before restart/change.
- Share user-facing behavior and UI by default; platform adapters supply OS mechanics. Document actual limitations in `public/site/src/features.json` and test visible behavior on every claimed platform before release.
- Keep changes owner-local and bounded. Move a legacy mechanism with its callers/tests, preserve contracts and verify consumers before removing donors. Coordinate real cross-owner contract changes; routine owner work need not wait for an integrator.
- Delete verified dead implementations and obsolete tests/references rather than copying them into an archive. Establish requiredness from consumers, build/runtime/package inputs, supported compatibility/data readers and owner reservations—not merely deployment. Preserve active/uncommitted work, private captures, credentials and evidence. See `enablement/refactor.md` for campaign gates.

## Language policy

Use TypeScript for product behavior, web code, scripts, tests and repository tooling. Reserve Rust for capture/media execution and narrow native resource, durability and safety mechanisms; preserve platform-native adapters where needed. Connect and Public target zero repo-owned Rust and no Rust build dependency, including their clients, CLI behavior, tests and packaging. Desktop and Agent consume published Engine capabilities rather than importing its implementation. Shared packages and composition must not reintroduce a Rust build into a TypeScript owner's development loop. The accepted boundary, current migration debt and proof of independence are defined in [value-stream language boundaries](shared/docs/value-stream-boundaries.md). Existing Rust remains authoritative until a verified replacement and its callers land; this direction does not authorize a wholesale rewrite or claim independence already exists.

Do not add Python or authored JavaScript files (`.js`, `.jsx`, `.mjs` or `.cjs`) without explicit user approval. Existing Python and JavaScript may receive necessary fixes; migrate them in bounded, verified changes rather than starting an unrelated rewrite. Preserve native adapters and tool-required configuration formats. Generated deployment JavaScript stays outside Git.

## Desktop UI direction

Electron is the selected desktop UI shell, prioritizing a shared macOS/Linux experience and fewer rendering differences. This is the target direction, not a claim that migration is implemented. Keep live capture and native media execution in Rust/native adapters, independent of TypeScript product policy, UI animations and responsiveness; measure pill responsiveness and resource contention on both platforms. Processing orchestration and output policy may live in TypeScript while native workers execute expensive operations. Native adapters may still be needed for OS integration; the exact overlay boundary remains to be established.

**Migrate what you touch—within the task, not as a separate campaign.** When a Desktop task changes a user-facing workflow, include its Electron + React/TypeScript + shadcn implementation in the same PR (`capture/desktop/ui/frontend`; canonical controls in `shared/ui`). Carry the smallest coherent workflow slice needed to make that change usable end to end, even when it extends beyond the exact component or lines requested; do not leave a legacy-only improvement or defer the touched slice to a separate migration issue. Do not turn this into a wholesale rewrite, unrelated adjacent migration, or new migration-only prerequisite. Reuse existing frontend/bridge contracts; put migrated product policy and its persistence with the TypeScript owner, keep native capture safety/resource enforcement in the Engine, and keep OS mechanics in native adapters. Existing Rust policy/persistence remains authoritative until each coherent replacement and its consumers are verified; never introduce competing writers. Keep the old path for surfaces not yet replaced; do not render two competing implementations of the same surface. Preserve a working old path until its replacement is accepted, then remove it when its consumers/build/package inputs are verified. Document routing/rollback and the removal condition for changed surfaces, and verify shared behavior and affected platform boundaries under the Desktop verification policy below. This requirement does not itself switch installed routing, enable existing experiments, authorize unrelated migration, or waive consent, safety or release requirements.

Desktop is a fast capture-and-handoff tool, not a workspace: no desktop review screen; most conventional UI belongs in infrequently opened Settings. The Loom-like recording-sharing workspace for coworkers and their agents belongs in web/Connect. Reuse UI components where useful without embedding that workspace in Desktop. Shared UI does not replace platform checks for permissions, capture, focus, overlays and packaging.

Minimize both stop-to-paste and stop-to-watch delays. Connect links are expected to be the common handoff and may be copied before upload/processing completes; a recipient-facing “Preparing recording” state is acceptable. Keep “link copied” distinct from “ready to watch”; never present the former as proof of the latter. This direction does not authorize an unscoped migration or release.

## Ownership and layout

The accepted ownership target is Engine, Desktop and Agent under `capture/`, with `connect`, `public`, `shared` and `enablement` as separate owners. Their dependency direction is architectural: Desktop and Agent may consume published Engine capabilities; Engine depends on neither and never on Connect or Public product implementation. Keep capture-internal shared mechanisms in `capture`. The current root Rust application uses ordinary modules; do not add path shims, extra crates or services to simulate ownership. The language-boundary target requires independently usable TypeScript packages and native capability contracts, not a new service per owner; change runtime/package boundaries only in a scoped, verified adoption slice.

Production sources and owner materials have physically relocated: the standalone Engine core is in `engine/core/`; legacy Engine runtime, bundle, export, native and docs remain under `capture/engine/` in the root application. Desktop code/docs/native files and performance tools are in `capture/desktop/`; Agent code, proof/narrator tools, skills and docs are in `capture/agent/`. `composition/` holds CLI/composition code, `shared/` cross-stream code/docs, and `enablement/` repository verification and refactor guidance. `public/site/scripts/og-video/` and `public/site/scripts/motion/` hold marketing video tooling. These are physical paths within the root application, not proof that all production behavior has been adopted into an independently running Engine. Treat the ownership and dependency direction above as the target; do not claim that migration is complete.

For repo-owned source, assets, docs and tooling, target at most 10 immediate files and 10 immediate directories per directory. Count hidden repo-owned entries; exclude generated output, dependencies, build caches and Git internals. Keep tool-required exceptions (such as root Cargo manifests, `.github`, `.githooks`, `.cargo`) visible and explicitly bounded; do not hide or misclassify overfull directories. Keep docs minimal and beside their owner; retain non-obvious constraints, avoid duplication, and do not add `root/docs/` material.

## Understand, change and verify

Read the relevant owner docs before changing a subsystem. Keep `Cargo.toml` and `Cargo.lock` stable unless explicitly required. After Rust changes, rebuild before running `target/debug/apparent` (`cargo test` does not rebuild it). For broad root checkpoints use `cargo build -j 3 --offline` and `cargo test -j 3 --offline -- --test-threads=2` (on macOS add `taskpolicy -c utility`); on Clanker run each heavy command or hook-backed push once through `/home/simon/.local/bin/t3-build`, never nested, honoring `T3_BUILD_JOBS`.

Verification is proportional to changed behavior, not commit IDs. For mechanical moves verify preserved content/build inputs, imports/visibility, affected compilation on macOS/Linux and focused existing tests. Reuse evidence only for unchanged inputs and state its source. Broad suites are for shared/build/security/lifecycle changes, integration checkpoints or uncertain impact. New native proof is for changed native behavior. Never turn an unrun check into a pass or waive unresolved failures/platform gates; investigate red tests, fix the underlying issue and rerun focused then full affected-platform tests.

**Desktop verification:** Run the shared React/Electron behavior matrix and real Rust↔Electron bridge checks on Linux. Do not repeat that matrix on Mac merely because a shared UI workflow changed. Before merge, require focused shared checks plus native proof only for affected OS boundaries: permissions, native dialogs, shortcuts/input, clipboard/paste, window ownership/focus/stacking, capture inclusion/exclusion, startup/fallback and packaging. Changed Electron/runtime or bridge contracts require assessment of affected consumers on each platform; a Linux mock is not proof of a Mac effect. A shared-renderer-only change may merge without a fresh Mac walkthrough when the owner establishes that the native boundaries are unchanged and records applicable prior evidence. First adoption of a native route still needs its affected seam checks. Before Mac publication, retain a short smoke of the current packaged app (launch, representative interaction and cleanup), applicable native evidence and exact-commit CI/signing gates. Reuse deeper seam proof only after checking its relevant source, dependencies, runtime, packaging and environment inputs; unrelated main advances alone do not invalidate it. Missing evidence for an affected seam requires that focused check, not a full workflow certification campaign. See `capture/desktop/docs/native-testing.md` for the coverage split and transition rules.

`.githooks/pre-push` runs cheap selector, hook and release-admission contracts for
feature pushes while preserving exact-HEAD/clean-tree guards. Explicit local
`enablement/verification.py --run` and direct main pushes retain conservative
changed-tree build/tests. Value-stream delivery runs automatically on PRs targeting
main and on matching main pushes. PRs run fresh owner checks/builds without
publishing; require applicable Value-stream PR checks before merge. Other workflows,
including standalone Linux/macOS and Connect verification, are manual-only.
Feature-branch pushes without a PR do not trigger CI. Before merging a PR,
run focused checks, independent review, current-base integration checks and required
native/platform proof; do not dispatch standalone full branch CI. Linux and web publication require the
exact commit's successful Linux/shared verification; Mac publication additionally
requires its successful Mac verification. A queued or failed Mac run does not block
Linux publication, and Linux success never substitutes for Mac verification. Native/product acceptance still applies to changed
behavior. Fetch main before publishing; feature planning compares the full delta

When output/UX changes or a capture test affects output, inspect the relevant real bundle's text and images; for mechanical moves reuse relevant evidence after checking source/import/build-input preservation. Report unavailable evidence and concrete output/UX issues; do not make a capture solely because files moved. Documentation/tooling-only changes need no bundle inspection.

For changed Linux native behavior, a Mac build on Linux is not a Linux test. Follow the Linux/Omarchy procedure in `capture/desktop/docs/linux/linux.md`, inspect the actual Linux checkout instructions and VM launcher, and test the affected boundary in the isolated VM. Shared Electron behavior may use the Linux renderer/bridge lane above without a new guest walkthrough. Check for existing Apparent VM processes before staging/launching; never replace a worker's app or substitute a host build, `--help`, or X1 install for a required GUI test. For affected Mac Settings/native/cabled-mirror boundaries, use a Mac. See `capture/desktop/docs/onboarding-and-settings.md` and `capture/desktop/docs/native-testing.md`.

## Parallel agent work

Proactively use subagents when independent investigation, implementation slices, test preparation or review can shorten delivery. Give each child a bounded outcome, relevant context, acceptance evidence and explicit file/resource ownership. Keep the parent on useful independent work while children run, following the harness's completion and yield instructions. Start with one or two helpers when useful; simple edits and tightly coupled work may stay with one agent. Check existing owners first, isolate concurrent writers, and admit expensive builds/native runs against actual shared capacity and existing budgets.

For Codex parents, default subagents to the latest available Luna model, currently `gpt-6-luna`. Discover the current provider model catalog and explicitly select that model rather than inheriting the parent's model. Follow the harness's native-versus-T3 delegation routing. Explicit user model choices override this default; if Luna is unavailable, report that and obtain a model choice before substituting. The parent owns integration, consumes completion results, resolves findings and continues through the original acceptance and delivery gates. Delegation does not create new spending, access or release authority.

## Deliver, safety and consent

At assignment start, identify the requested artifact, checks/platform proof and applicable authority. For work Simon authorizes in `tryapparent/apparent`, the issue owner continues through merge without another code-review or merge approval once every applicable pre-merge Definition of Done is verified: independent review, focused tests and required native/platform evidence for the candidate, current-base integration checks, privacy and cleanup. Value-stream CI runs on PRs and again after merge on main; applicable PR checks must pass before merge and main receipts gate publication. Standalone full verification remains manual-only. Never waive a requirement, bypass protection or treat partial completion as done. Normal, understood automatic CD consequences are authorized; separate activation, destructive migration, access, spending and external-message restrictions remain. Explicit task limits and PR holds win. For other work, normally deliver a scoped commit and draft PR; a draft PR alone grants no further authority. Verify what actually landed and report it. Never include secrets, private evidence or another writer's work in a delivery.

- Own the accepted outcome, not just a dispatch or readiness receipt. Use existing task/PR completion notifications, consume their results and continue feasible work. A running badge, queued message or published draft is not completion. Ask Simon only for a genuinely uncovered decision, not a repeat of existing authority.
- For a stream rebuild or feature-parity assignment, retain a compact inventory from the user's scope and the authoritative existing workflows/commands. Distinguish implemented behavior, fixture-only behavior, installed adoption, verification gaps, explicit exclusions and blocked features. A merged package, adapter or prerequisite completes its slice, not the stream. After each merge, select the next authorized feature that can advance; a missing native capability blocks its actual consumers, not unrelated CLI, UI, persistence or compatibility work. Do not invent extra scope to keep working.
- A dependency handoff does not transfer the waiting owner's remaining implementation responsibility. Before yielding, identify the exact missing capability, producer and committed-artifact/evidence condition that will unblock it, and establish an existing supported completion route back to the waiting owner. If only an owner-to-owner handoff is supported, obtain an explicit commitment to notify that owner on the condition; sending a request alone is not a registered wait. If no route is available, report that specific notification limitation rather than promise automatic resumption. On wake, inspect the actual capability: an unrelated prerequisite merge or completed run does not clear the blocker. Preserve explicit user waits and holds; do not create pollers, duplicate owners or repeated nudges.
- When post-merge CI or publication is part of the accepted outcome, retain ownership through its relevant result using the supported completion mechanism. Do not stop at "merged; live CI unverified" without a truthful continuation or named blocker. A successful workflow whose relevant jobs were skipped is not verification or publication proof. Inspect superseding runs and declared input/artifact reuse before reusing earlier evidence; do not require unrelated workflows or requalify unchanged native seams.
- When a merge breaks main CI, the merging agent owns the repair. Other agents check existing repair work and continue independent tasks rather than implementing competing fixes. If that owner is unavailable or attribution is unclear, an agent blocked by the failure may take over: first check for an active fixer and state ownership in the existing task or PR before editing; no separate repair issue or approval is required. Respect active writers and explicit holds, keep unaffected work moving, and preserve all applicable verification and publication gates.
- Deliver authorized implementation work through short-lived, independently safe PRs against current `main`, not a long-lived umbrella branch. Commit each coherent change after focused checks pass, before starting the next concern; commits are checkpoints, not task completion. At kickoff and in implementation briefs, identify the next mergeable behavior or necessary compatible prerequisite, its dependencies, non-goals and observable proof; do not require a speculative full issue breakdown. Merge each ready slice after its applicable review, tests, native/platform proof and CI gates, then base dependent work on updated `main`. Each slice must keep trunk usable under existing deployment behavior; splitting work does not waive integration evidence, consent or release holds, or authorize hidden/off-by-default features. Keep the issue open and retain ownership until the full requested outcome passes acceptance. For existing large branches, preserve their work and evidence, then port complete dependency-closed slices onto current `main`; do not discard work, import the entire umbrella, or take over another owner's files. Independent work need not wait for unrelated slices.
- Before finalizing an implementation turn, compare the requested outcome with the actual evidence. If a concrete safe, authorized next step remains, execute it rather than ending with a promise to do it later. A failed diagnostic followed by cleanup is a checkpoint, not completion when useful offline investigation or repair remains. Stop for verified completion, an explicit user pause, or a specific missing decision/access/resource that prevents further useful work; yield for a registered completion notification when no independent work remains, honoring the harness's explicit delegation and PR-watch yield rules. Do not poll, duplicate owners, repeat capped attempts, widen scope or bypass approval to keep moving. Analysis-only requests end with the requested analysis. When necessary for the accepted outcome, make the smallest prerequisite repair, demonstrate the failure, preserve acceptance, add faithful regression coverage, obtain proportionate independent review and verify the combined result. ## Product gates and operations

New user-facing features, including handoff/output changes, ship enabled by default; do not add an off-by-default experiment unless explicitly requested. Preserve consent, permission and safety gates. This policy does not itself enable existing experiments. Config is `~/.config/apparent/config.json`, the code checks `shared::handoff::experiment("<name>")`, tests use `shared::handoff::enable_experiment`, and `apparent reprocess`/`inspect` accept `--experiment <name>`. Invalid config values are skipped/logged and a bad key drops only that key. Current flags and output contract: `capture/engine/docs/keyframes-and-text.md`.

Keep `public/site/src/features.json` accurate in the same PR when adding/removing/renaming a user-facing feature or changing its status. It records status, platforms, shortcuts, config keys and docs; release changes `main` entries to `stable@<version>`. `cargo test feature_map` checks code/config entries. Release procedures: `capture/desktop/docs/release.md`.

Install/launch the Mac app through `capture/desktop/scripts/packaging/install-app.sh`, not a `target/` daemon: cleanup can unlink it and disturb TCC identity. For remote Mac installs use `capture/desktop/scripts/packaging/install-app-remote.sh`; release signing and update storage stay outside `target/` and `/tmp`. Details and recovery are in `capture/desktop/docs/onboarding-and-settings.md` and `capture/desktop/docs/release.md`.
