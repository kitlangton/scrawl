# Apparent: Agent Instructions

Apparent records screen, voice, cursor, clicks and ink so a human can point, talk and draw while an agent builds. It produces `.apparent` bundles for inspection and handoff. Supported platforms are **macOS and Linux**; do not add Windows support, tests, release assets or new docs. Existing Windows code is not a support promise; retire it only in a separately scoped, verified change.

## Product invariants

- Minimize human effort: capture, marking and handoff should be quick. Record known window, element, URL and session context instead of making agents infer it from pixels or vague references.
- Keep images visual and text semantic. Preserve time-aligned transcript, interactions and absolute paths in bundle text; avoid rasterized captions/card chrome. Cut keyframes on meaningful action or visual change, not speech pauses; retain full frames when cropping. See `capture/engine/docs/keyframes-and-text.md`.
- Persist user-controlled settings and feature flags in documented, inspectable config (currently `~/.config/apparent/config.json`). Settings writes update it; file edits apply at a documented time. Preserve unrelated keys and secrets. Reconcile OS-owned effects such as permissions and login registration; config values alone do not prove application. Active capture state is runtime state, but must be discoverable before restart/change.
- Share user-facing behavior and UI by default; platform adapters supply OS mechanics. Document actual limitations in `public/site/src/features.json` and test visible behavior on every claimed platform before release.
- Keep changes owner-local and bounded. Move a legacy mechanism with its callers/tests, preserve contracts and verify consumers before removing donors. Coordinate real cross-owner contract changes; routine owner work need not wait for an integrator.
- Delete verified dead implementations and obsolete tests/references rather than copying them into an archive. Establish requiredness from consumers, build/runtime/package inputs, supported compatibility/data readers and owner reservations—not merely deployment. Preserve active/uncommitted work, private captures, credentials and evidence. See `enablement/refactor.md` for campaign gates.

## Incremental migration and language policy

**Every feature should advance the target architecture in the area it touches.** At kickoff, name the smallest usable migration slice, its target owner, dependencies and observable proof. Implement new product behavior in TypeScript and migrate touched legacy policy with its callers, persistence and tests in the same PR. Keep this tied to the requested outcome; do not start an unrelated rewrite. If a concrete dependency prevents safe adoption, state that dependency and the remaining debt explicitly. Necessary bounded correctness/security repairs in existing Rust/native code remain allowed.

Record is the target headless TypeScript owner of capture-to-handoff workflow, recording preferences, local retention, default keyframe/transcript/bundle assembly and ordinary export policy. Agent owns inspection, targeted extraction and proof recipes; Desktop owns human controls and shell presentation. Agent consumes Record for the standard outcome; Record consumes Engine native capabilities. Agent may also use Engine directly for specific operations. These are target boundaries, not claims that these independent packages already exist. Connect owns delivery/viewing policy. Shared holds reusable UI/schemas/utilities, not displaced owner policy. Keep one authoritative persistence mutation contract across languages; preserve formats, unrelated config keys and secrets. Prove owner build independence with supported commands in a clean environment without Rust tools or cached Rust outputs.

Use TypeScript for product behavior, web code, scripts, tests and repository tooling. Reserve Rust for capture/media execution and narrow native resource, durability and safety mechanisms; preserve platform-native adapters where needed. Connect and Public target zero repo-owned Rust and no Rust build dependency, including their clients, CLI behavior, tests and packaging. Desktop and Agent consume published Engine capabilities rather than importing its implementation. Shared packages and composition must not reintroduce a Rust build into a TypeScript owner's development loop. Existing Rust remains authoritative until a verified replacement and its callers land; this direction does not authorize a wholesale rewrite or claim independence already exists.

Do not add Python or authored JavaScript files (`.js`, `.jsx`, `.mjs` or `.cjs`) without explicit user approval. Existing Python and JavaScript may receive necessary fixes; migrate them in bounded, verified changes rather than starting an unrelated rewrite. Preserve native adapters and tool-required configuration formats. Generated deployment JavaScript stays outside Git.

## Desktop UI direction

Electron is the selected desktop UI shell, prioritizing a shared macOS/Linux experience and fewer rendering differences. This is the target direction, not a claim that migration is implemented. Keep live capture and native media execution in Rust/native adapters, independent of TypeScript product policy, UI animations and responsiveness; measure pill responsiveness and resource contention on both platforms. Processing orchestration and output policy may live in TypeScript while native workers execute expensive operations. Native adapters may still be needed for OS integration; the exact overlay boundary remains to be established.

Preview 0.12.2 (`preview-mac-12-2`, `cbaa8f74c`) remains the macOS development baseline with matching Linux AppImages. Use `migration/main-preserved-2026-11-08` for reviewed, bounded ports rather than merging the umbrella branch or claiming its packages already exist on main.

**Migrate what you touch—within the task, not as a separate campaign.** When a Desktop task changes a user-facing workflow, include its Electron + React/TypeScript + shadcn implementation in the same PR (`capture/desktop/ui/frontend`; canonical controls in `shared/ui`). Carry the smallest coherent workflow slice needed to make that change usable end to end, even when it extends beyond the exact component or lines requested; do not leave a legacy-only improvement or defer the touched slice to a separate migration issue. Do not turn this into a wholesale rewrite, unrelated adjacent migration, or new migration-only prerequisite. Reuse existing frontend/bridge contracts; put migrated product policy and its persistence with the TypeScript owner, keep native capture safety/resource enforcement in the Engine, and keep OS mechanics in native adapters. Existing Rust policy/persistence remains authoritative until each coherent replacement and its consumers are verified; never introduce competing writers. Keep the old path for surfaces not yet replaced; do not render two competing implementations of the same surface. Preserve a working old path until its replacement is accepted, then remove it when its consumers/build/package inputs are verified. Document routing/rollback and the removal condition for changed surfaces, and verify shared behavior and affected platform boundaries under the Desktop verification policy below. This requirement does not itself switch installed routing, enable existing experiments, authorize unrelated migration, or waive consent, safety or release requirements.

Desktop is a fast capture-and-handoff tool, not a workspace: no desktop review screen; most conventional UI belongs in infrequently opened Settings. The Loom-like recording-sharing workspace for coworkers and their agents belongs in web/Connect. Reuse UI components where useful without embedding that workspace in Desktop. Shared UI does not replace platform checks for permissions, capture, focus, overlays and packaging.

Minimize both stop-to-paste and stop-to-watch delays. Connect links are expected to be the common handoff and may be copied before upload/processing completes; a recipient-facing “Preparing recording” state is acceptable. Keep “link copied” distinct from “ready to watch”; never present the former as proof of the latter. This direction does not authorize an unscoped migration or release.

Record is the target headless workflow owner described above. Their dependency direction is architectural: Record, Desktop and Agent consume published Engine capabilities; Engine depends on none of their product implementations or on Connect/Public. Keep capture-internal shared mechanisms in `capture`. The current root Rust application uses ordinary modules; do not add path shims, extra crates or services to simulate ownership. Adopt independently usable TypeScript packages and native capability contracts only in scoped, verified slices.

Production sources and owner materials have physically relocated: Engine code/docs/native files are in `capture/engine/`; Desktop code/docs/native files and performance tools are in `capture/desktop/`; Agent code, proof/narrator tools, skills and docs are in `capture/agent/`. `composition/` holds CLI/composition code, `shared/` cross-stream code/docs, and `enablement/` repository verification and refactor guidance. `public/site/video-demo/` holds marketing video tooling. ## Temporary artifacts on Clanker

Put new agent-created development files outside repository source in a private per-job directory directly under `/tmp`: `/tmp/apparent-dev-<job>-<run>/` (for example, `mktemp -d /tmp/apparent-dev-<job>-XXXXXX`). This includes helper scripts, diagnostics, reports, generated build/test output, screenshots, proof media, synthetic fixtures and disposable VM runs/overlays. Point temporary/output paths there; do not accumulate these artifacts under home, `~/.local/share`, `~/.local/state`, `Projects` or `/srv`. Keep each job in its own direct child of `/tmp`, matching the installed cleanup depth.

These artifacts may be cleaned during active verification. Regenerate missing output; activity, verification needs and expensive recreation do not create retention exemptions. This supersedes older disposable-development-artifact location examples in owner guides or skills.

Canonical repositories and Git metadata, provider histories, credentials, required runtime/application data and configuration, installed tools, existing bounded shared caches, reusable VM templates and their backing dependencies, and real private user captures keep their proper locations. Durable development evidence outside `/tmp` requires an explicit user retention request; preserve existing exact retention requests and their release conditions. This governs new files, not relocation/deletion of existing data or changes to cleanup/service configuration.

## Understand, change and verify

Read the relevant owner docs before changing a subsystem. Keep `Cargo.toml` and `Cargo.lock` stable unless explicitly required. After Rust changes, rebuild before running `target/debug/apparent` (`cargo test` does not rebuild it). For broad root checkpoints use `cargo build -j 3 --offline` and `cargo test -j 3 --offline -- --test-threads=2` (on macOS add `taskpolicy -c utility`); on Clanker run each heavy command or hook-backed push once through `/home/simon/.local/bin/t3-build`, never nested, honoring `T3_BUILD_JOBS`.

Verification is proportional to changed behavior, not commit IDs. For mechanical moves verify preserved content/build inputs, imports/visibility, affected compilation on macOS/Linux and focused existing tests. Reuse evidence only for unchanged inputs and state its source. Broad suites are for shared/build/security/lifecycle changes, integration checkpoints or uncertain impact. New native proof is for changed native behavior. Never turn an unrun check into a pass or waive unresolved failures/platform gates; investigate red tests, fix the underlying issue and rerun focused then full affected-platform tests.

`.githooks/pre-push` runs cheap selector, hook and release-admission contracts for
feature pushes while preserving exact-HEAD/clean-tree guards. Explicit local
`enablement/verification.py --run` and direct main pushes retain conservative
changed-tree build/tests. Repository checks run the cheap contracts and workflow
validation automatically on PRs and main pushes. Full Linux/macOS verification
and all publication workflows remain manual-only. Linux and Connect publication require the
exact commit's successful Linux/shared verification. Public publication uses its own
successful web/shared checks and sealed artifact in `stream-public.yml`, without
requiring Rust, Desktop or Connect verification. Mac publication additionally
requires its successful Mac verification. A queued or failed Mac run does not block
Linux publication, and Linux success never substitutes for Mac verification. Native/product acceptance still applies to changed
behavior. Fetch main before publishing; feature planning compares the full delta
from its merge-base. Details: `enablement/docs/continuous-delivery.md`.

When output/UX changes or a capture test affects output, inspect the relevant real bundle's text and images; for mechanical moves reuse relevant evidence after checking source/import/build-input preservation. Report unavailable evidence and concrete output/UX issues; do not make a capture solely because files moved. Documentation/tooling-only changes need no bundle inspection.

For Linux-facing changes, a Mac build on Linux is not a Linux test. Follow the Linux/Omarchy procedure in `capture/desktop/docs/linux/linux.md`, inspect the actual Linux checkout instructions and VM launcher, and test the exact candidate in the isolated VM. Check for existing Apparent VM processes before staging/launching; never replace a worker's app or substitute a host build, `--help`, or X1 install for a GUI test. For Mac Settings/native/cabled-mirror proof, use a Mac. See `capture/desktop/docs/onboarding-and-settings.md` and `capture/desktop/docs/native-testing.md`.

Normal, understood automatic CD consequences are authorized; separate activation, destructive migration, access, spending and external-message restrictions remain. Explicit task limits and PR holds win. For other work, normally deliver a scoped commit and draft PR; a draft PR alone grants no further authority. Verify what actually landed and report it. ## Product gates and operations

New user-facing features, including handoff/output changes, ship enabled by default; do not add an off-by-default experiment unless explicitly requested. Preserve consent, permission and safety gates. This policy does not itself enable existing experiments. Config is `~/.config/apparent/config.json`, the code checks `shared::handoff::experiment("<name>")`, tests use `shared::handoff::enable_experiment`, and `apparent reprocess`/`inspect` accept `--experiment <name>`. Invalid config values are skipped/logged and a bad key drops only that key. Current flags and output contract: `capture/engine/docs/keyframes-and-text.md`.

Keep `public/site/src/features.json` accurate in the same PR when adding/removing/renaming a user-facing feature or changing its status. It records status, platforms, shortcuts, config keys and docs; release changes `main` entries to `stable@<version>`. `cargo test feature_map` checks code/config entries. Release procedures: `capture/desktop/docs/release.md`.

Install/launch the Mac app through `capture/desktop/scripts/packaging/install-app.sh`, not a `target/` daemon: cleanup can unlink it and disturb TCC identity. For remote Mac installs use `capture/desktop/scripts/packaging/install-app-remote.sh`; release signing and update storage stay outside `target/` and `/tmp`. Details and recovery are in `capture/desktop/docs/onboarding-and-settings.md` and `capture/desktop/docs/release.md`.
